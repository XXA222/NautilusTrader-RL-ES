# Nautilus-RLES · AI-05 / L5 第二轮功能说明

## 2026-10-13 当前集成增量：策略输入尺度

- `ActorGenomeSpec(version=2, input_scale=...)` 声明与观测逐列对应的不可变、有限正数尺度；`rles_es_evotorch.actor.policy_inputs()` 在神经网络前应用，`act()` 自动使用。v2 签名及 genome hash 包含尺度；v1 identity-input 的签名保持兼容，禁止在 v1 下偷偷改变尺度。
- 应用新建 E1 路线 A1/A3/A4 默认 `es_input_scaling='account_units'`；金额按声明 starting capital、ETH 数量按首个 Train 可见 mark/risk budget 转换，其余字段维持原值。`none` 可显式保留旧语义。原生账户/订单/奖励事实不改写；策略变换和原观测单位分别保存。
- candidate worker、ES bundle 加载与 E1 teacher 共用同一 Actor 规格。run manifest 保存规格，恢复时重建比较；旧无该字段的 checkpoint 保持 v1 后再校验原 recipe 和 RunSpec，不自动升级历史模型输入域。
- v2 E1→R1 的首层参数组合固定输入尺度和已在 Train teacher 语料上校准的 L4 均值/标准差；完整覆盖和 parity 门继续生效。BC early stop 只有在整份训练语料通过原容差时才允许结束，实际 epoch 写入 DistillationEvidence，最大预算保留在配置中。
- v2 E1→PPO 还显式映射末端 tanh：标准 SB3 policy 增加标量 Tanh 节点，再接初始化为 action scale 的最终 affine head；源/目标规格分别记录，新增 head 属于确定性构造，不冒称源 genome 既有参数。Train 校准的固定 clip_obs 覆盖该语料，避免输入被丢失；旧 checkpoint 保持原架构。原生 SB3 更新公式不改。

## 2. 路线、Actor/Genome 与参数

路线只允许：A0=R1；A1=E1；A2=R1→E2；A3=E1→R1；A4=E1→R1→E2。一个 orchestrator 对象一次只能执行一个完整周期，不允许 E1↔R1↔E2 不限次交替。

- `ActorGenomeSpec(observation_names, hidden_sizes, activation="tanh", output_size=1, action_scale=1.0, dtype="float32", version=1)`：名称必须唯一、有序，隐藏层固定，动作区间 `[-action_scale,+action_scale]` 且不越过 `[-1,1]`。`shapes / size / signature` 固定；`encode/decode` 拒绝缺失/多余层、不匹配 shape/dtype、NaN/Inf；`genome_hash` 与 `actor signature` 绑定。
- `FitnessSpec`：非负权重，`score(split="train_inner", net_return, tail_loss, max_drawdown, constraint_violations)`；所有非训练区直接拒绝。`score_episode` 从初末 native equity、逐步未整形 log return、逐步 drawdown 和风险干预事实生成 net return、worst-tail CVaR loss、最大回撤与约束项；tail fraction 由评估配方显式冻结，不以 L3 shaped reward 给 ES 打分。
- `SoftRiskDimension(name, lower, upper)`：名称白名单为 `exposure_multiplier`、`drawdown_throttle`、`volatility_throttle`，满足 `0 <= lower < upper <= 1`；不允许向 E2 传递 HardRisk 参数。`SoftRiskSpace.from_latent` 将 CMA-ES 产生的无界向量映射到各维度区间内。**映射绝不替代 L3 的 HardRiskGuard。**
- `EvolutionConfig(algorithm, population_size, generations, seed, stdev_init, center_learning_rate, stdev_learning_rate, max_evaluations, device, gpu_lease_id)`：PGPE 要求种群偶数；任何 ES 最多执行预算内的真实候选评估；PGPE/CMA-ES 都需合法初始化扩散参数。`device=cpu` 默认，若设置 `cuda:<index>` 必须由 L6 注入 GPU lease ID，CUDA 不可用直接阻断，不回退 CPU；Nautilus 执行仍在 CPU。`EvoTorchProvider.evolve(dimension, initial_bounds, center)` 返回 `EvolutionResult`；E2 必须传入 `SoftRiskSpace`，E1 不得传入。
- `TrainInnerEvaluator(candidate, *, split)`：只允许外部事实层以 `split="train_inner"` 提供 fitness。算法库负责分布更新，L5 不实现更新公式。

**EvoTorch 兼容性注意**：部分 CMA-ES 实现明确拒绝直接受边界约束的 `Problem`。本实现只给 EvoTorch *初始范围*，不设置硬 `Problem.bounds`，由 `SoftRiskSpace.from_latent` 将每个优化候选约束到软风险可行区间。必须仍由 G0 在目标 EvoTorch 精确版本复核 PGPE/CMA-ES 的构造参数、采样、评估和状态接口。

## 3. 候选评估 / Checkpoint 接口

- `CandidateRequest`：必须提供 `run_id, attempt_id, generation, candidate_id, episode_id, seed, genome, actor_signature, candidate_kind, candidate_schema_hash, account_isolation_id, split="train_inner"`。E1 的 `candidate_kind="actor"`，`candidate_schema_hash` 固定 L5 ActorGenome 搜索布局；`actor_signature` 可单独绑定计划中的 R1 Actor 契约，两者职责不同。未指定下游身份时，actor signature 默认采用 ActorGenome schema 签名。E2 的 `candidate_kind="soft_risk"`，`actor_signature` 固定为 R1 Actor，`candidate_schema_hash` 则是独立 SoftRiskSpace 签名。`request_hash` 绑定候选向量、搜索 schema 和完整执行身份。
- `CandidateResult`：必须携带与请求一致的 run/attempt/generation/candidate/episode/seed、`request_hash`、`account_isolation_id`、有限 `fitness` 和 `evidence_hash`。
- `scenario_seed(root_seed, fold_id, generation, episode_id)`：不同候选共享同一 market scenario seed，**绝不共享账户**。
- `dispatch_generation(requests, dispatch=..., budget=EvaluationBudget(n, reserve_requests=... ), candidate_spec=..., actor_signature=...)`：支持 ActorGenomeSpec（E1）或 SoftRiskSpace（E2）；E1 的 genome schema 与下游 Actor contract 身份分开校验，E2 必须固定 R1 `actor_signature`，候选维数与 actor 参数维数不再混同。L5 提供调度/核算边界，L6 dispatch callback 负责实际异步候选引擎运行。若绑定 L6 SelectionLedger，`reserve_requests` 必须在 worker 派发前事务性预留整批逻辑请求；即使 worker 崩溃/部分执行失败，费用仍计入协议全局 ES budget，换 attempt 重跑也不能免费。乱序归并按 `(run,attempt,generation,candidate,episode,seed)`；缺项、重复、越界、错 schema/Actor/账号、错请求哈希、中途失败均报错。
- E2 的 `CandidateRequest.genome` 使用有序 SoftRisk 物理乘数；统一派发入口逐请求执行 `SoftRiskSpace.decode` 并再次验证上下界，不能依赖上游 CMA-ES latent 映射来保护 DTO 边界。
- `GenerationLaneEvaluator`：接收 EvoTorch 的完整 float32 种群，按代际及固定 fold/seed 生成候选×episode CRN 矩阵；候选按原行序获得跨场景 fitness 均值。E1 可传入独立的 R1 Actor contract 身份；其 `signature` 绑定 run/attempt/fold、种子、场景、候选 schema、Actor 和 dispatch 身份，可作为 Provider 的 `batch_fitness_id`，因此 checkpoint 恢复会拒绝评估配方变化。
- `WorkerLaneDispatcher`：将 L5 请求转换为 L6 keyed batch，并自动注入保留字段 `rles_context`（包含请求哈希、genome、scenario seed、隔离账号、schema 与 Train-inner split）。worker 必须回显 `request_hash` 和 `account_isolation_id`，不匹配则拒收；同时返回初末权益、逐步未整形 log returns、drawdowns、风险干预量和 SHA256 `evidence_hash`。L5 据冻结 `FitnessSpec`/tail fraction 计算 episode fitness。payload builder 只映射其余业务参数到 L3 的冻结 evaluate schema，其显式 SHA256 身份参与 dispatcher 指纹。L5 不导入 L6 包，worker JSON 上限、执行超时和进程隔离由 L6 实施。
- `EvoTorchProvider(..., batch_fitness=..., batch_fitness_id=...)`：启用 EvoTorch `Problem(vectorized=True)`，每次完整种群只发起一次批量评估，再按行返回 fitness；`EvolutionResult.evaluations` 计候选数，`EvaluationBudget` 计候选×episode 请求数。已注册的 `nautilus_rles.es/evotorch` Provider 工厂接受相同批量参数；batch-only 模式无需伪造 scalar evaluator，且逐候选 `evaluate()` 会明确拒绝。未提供批量 evaluator 时保留原逐候选接口。
- `ESCheckpointEnvelope`：算法、数据/Actor/配置签名、attempt、代数、评估数量、数据游标、精确 native codec ID，以及 `distribution / optimizer / population / rng_torch / rng_numpy / rng_python / rng_evotorch / batch_evaluator / provider` 状态组件。EvoTorch **0.6.1 CPU** codec v2 使用白名单数值数组/JSON（`allow_pickle=False`），覆盖 PGPE 分布与 ClipUp 动量、CMA-ES 协方差/进化路径、最后完整种群、EvoTorch Problem generator、Torch/NumPy/Python RNG、最佳候选/计数，以及批量评估器已派发的逻辑请求和预算上限。`GenerationLaneEvaluator` 续跑会恢复 request keys，阻止已评候选重放或 genome 换值绕过额度；evaluator checkpoint schema v3 同时绑定 L6 durable reservation scope，恢复时会把整个 request-key 集合同 SQLite 预留精确对账，缺失、额外预留或协议/运行/尝试/阶段 scope 不匹配均在继续评估前拒绝。`evolve(..., generations=n)` 可在完整代际暂停，`continue_evolution()` 接续，`save(..., attempt_id, actor_signature, dataset_hash, config_hash)` 原子保存，`resume(...)` 在新 Provider 中还原。PGPE/CMA-ES 中断后候选序列与连续运行逐项一致测试已通过；失败恢复会回滚进程 RNG 并使实例失效。CUDA codec、非 0 数据游标及其他 EvoTorch 版本继续拒绝；不使用 pickle，不允许重初始化伪装 resume。

## 4. Transfer / Hybrid 公开接口

- `check_parity(algorithm, teacher, student, observations, actor_signature, absolute_tolerance)`：在固定 float32 观测集上比较确定性 `Box[-1,1]` 动作；返回 `ParityReport`（样本数、max/mean/p95/RMSE、观测哈希、签名、阈值、是否通过）。教师或学生重复输入产生不同输出则失败。
- `ParameterLoadEvidence`：预期/实际加载参数数量、缺失与额外键、shape/dtype 校验声明及 ActorSignature；参数不全**不视为直接权重迁移**。
- `transfer(...)`：L4 提供 `load_exact`、`reset_student`、`distill`、teacher/student；先尝试完整加载和动作 parity；若已确认结构不相容或 parity 失败，必须 reset 学生再执行 Train-inner 行为克隆；检查 teacher dataset hash 和实际 imitation MSE，再作动作 parity。不满足则停止。`DISTILLATION_NOT_WEIGHT_INHERITANCE` 明确区别于 `DIRECT`。
- `adapt_l4_load(loader, source_actor_signature, action_parity_mismatch=...)` / `adapt_l4_distillation(distill, student, epochs)`：L5 的可复用 L4 边界适配器，不导入 L4 包。前者仅将调用方指定的 L4 typed action-parity mismatch 转为 L5 可回退结构差异；所有 mapping/签名/shape/dtype 错误原样失败，并把 L4 exact-load/parity 证明转换为 L5 `ParameterLoadEvidence`。后者要求 L4 回报已通过的 behavioral-distillation，再由观测和标签重算训练集 SHA256 与 MSE。算法迁移仍需在 L4 source/destination mapping 和动作变换通过 ICR 后放行。
- `transfer_all(jobs, ...)`：PPO/SAC/TD3/DDPG 四模型都需独立目标身份及可用 L4 回调，任一失败则整批不得声明迁移完成。
- `StageBudget / StageUsage`：ES 包含 population / generations / evaluations，R1 包含 RL train steps。训练期间 Validation query 必须为零；查询/选择行为由 L6 SelectionLedger 另行治理。
- `StageUsage.from_rl_performance(s)` 按 L4 `Performance.samples` 提取 SB3 实际 timestep delta；多次 save/resume 训练必须传入该阶段每次 `train()` 的全部结果，由 adapter 求和。`StageUsage.from_evolution_result(result,population_size=...,lane_requests=...)` 按 L5 `EvolutionResult.generations/evaluations`、冻结 `EvolutionConfig.population_size` 和 L6 ESEvalLane 实际 candidate×episode 请求数分别记账。`StageBudget.max_lane_requests` 与 `max_evaluations` 是独立上限，二者均由 L6 SelectionLedger receipt 绑定。结构化适配避免 L5 对 L4/L5 Provider 包形成反向耦合。
- `StageArtifact.for_stage(...)` 从不可变 `RunSpec` 自动绑定 run fingerprint、parent 与 frozen data/feature/risk/execution hashes，并向注入的 L6 receipt provider 预取 usage receipt，再构造不可变 stage artifact。Runner 仍须提供实际训练结果、artifact payload hash、Actor/SoftRisk 输出及阶段 metadata；工厂负责把这些事实安全装入统一编排契约。
- `ProviderStageOutput` / `ProviderBackedStageRunner(stage,execute,receipt_provider)` 将以上步骤合并为正式 StageRunner：R1 只接受 L4 `Performance` 结果序列，E1/E2 只接受 L5 `EvolutionResult` 和 population size；自动推导并对照当前阶段预算，再创建 receipt-bound StageArtifact。它通过结构化结果保持 L5 对 L4/L6 的包依赖隔离，具体 env/provider/lane 工厂仍由集成应用注入。
- `GenerationLaneEvaluator.evidence_hash` 汇总每代 CandidateAggregate 与 worker evidence；该 generation evidence manifest 与 logical request budget 一起写入 EvoTorch checkpoint，并在 resume 中恢复、校验累计请求数。Stage Runner 应将此摘要纳入 ES artifact payload hash，使 L6 receipt 同时绑定优化产物与实际候选 episode 证据。
- `RunSpec`：冻结 run/attempt/route/算法/种子、`data/feature/config/hard_risk/execution/normalization/soft_risk_schema/initial_soft_risk/actor_signature` 指纹及各阶段预算。`RunSpec.fingerprint` 绑定所有字段。改变其中任何一个须产生新 run/attempt，不支持热修改。
- `Orchestrator(runners, attest_usage=...)`：调用注入的 E1/R1/E2 runner，要求每个返回与本阶段一致的 `StageArtifact`；L6 收据哈希必须与工件一致；E1/R1 保持初始 SoftRisk 不变、E2 保持 R1 actor 哈希不变。跨 E1→R1 的 artifact 必须带**类型化** `TransferResult` 且其哈希与报告一致。路由完成返回完整 lineage；异常进入 FAILED。
- `AblationPlan`：五个 RunSpec 中相同阶段使用同样的预算，输入数据、Actor、执行配置及种子一致。各路线的 route-specific `config_hash` 允许不同，但公共配方等价性最终仍需要 L1 manifest 确证。
- `build_lineage(artifacts)`：生成具有明确父子转换的图与 `lineage_hash`；生产持久化及 `COMPLETED` attempt registry 归 L1。

## 6. ICR（仅接口需求，不包含越权代码）

- `ICR-L5-01`：L1/L3 确认 `ActorSignature`、Observation 输入顺序/归一化、SoftRisk schema/硬风险指纹；L5 内部 V2 DTO 在正式 Contracts 冻结后通过适配层实现，不改 L1 文件。
- `ICR-L5-02`：L4 明确四算法 native mean actor loader、完整参数覆盖 / shape/dtype 校验、确定性 action 接口、重置学生、BC 返回数据和 imitation MSE。跨线必须适配本文 `TransferResult` 的结构化字段。
- `ICR-L5-03`：EvoTorch `Problem(vectorized=True)` → `GenerationLaneEvaluator` → 注入式 `WorkerLaneDispatcher` → L6 `ESEvalLane` 的 E1/E2 合成 spawn/IPC 链已本地验证；request/account 上下文会进入 worker payload 并要求回显。生产验收仍需 L3 冻结 `rles_context` 消费语义、真实候选级账户/Engine 隔离证据、SelectionLedger 收据与 L1 SeedTree；另需确认上层调度如何将同步代际调用放入其异步执行器。
- `ICR-L5-04`：L1 确定 immutable ArtifactStore、stage/optimizer checkpoint 持久化与 checkpoint 完整性标记的职责分配；禁止 L5 私自替换 L1 的最终运行存储。
- `ICR-L5-05 / G0`：CPython 3.14.7 + EvoTorch 0.6.1 CPU 上 PGPE/CMA-ES 初始化、多代更新、白名单状态编解码、Problem/global RNG 和恢复后候选序列等价性已由本地回归验证；仍需 clean wheel 环境重测，评估器非零数据游标恢复未实现，CUDA native codec 等待可用 CUDA runtime 验证。任何扩展版本须重新建立等价性证据，**不使用来源不明的 pickle 或宽松恢复**。

## 7. 依赖和兼容限制

生产包保持独立；不导入或修改任何 `nautilus_trader`、`stable_baselines3` 模块，也不访问 Nautilus cache/engine。ES 模块依赖 `NumPy + EvoTorch + PyTorch`；orchestrator 只需要 NumPy/标准库，不直接 import ES 实现包。`pyproject.toml` 声明可安装范围，**不是通过 G0 的依赖锁**；G0 通过后由最终集成人固定精确版本和 wheel/hash。
