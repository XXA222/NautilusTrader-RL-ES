## 1. 边界与责任

L1 为其余工作线提供**引擎中立**的不可变 DTO、运行 Protocol、Schema/版本政策、可信编解码、Provider Entry Points 发现、严格配置、运行身份、错误码和分层 SeedTree。Contracts 运行时只依赖 Python 标准库；Arrow IPC 为可选能力。

L1 **不实现** Nautilus Engine、交易撮合、资金费、手续费、风险裁剪算法、RL/ES 更新公式、并行调度器、WFO、模型训练或交易下单。`rles-contracts` 中不直接导入 `nautilus_trader`、`stable_baselines3`、`evotorch` 或 `torch`。Engine 的单一事实源仍为 L3 adapter，而非 DTO 自身。

**重要顺序条件**：总设计 G0→G1→G2；L1-002/003 的 CPython 3.14.7 实机安装、CPU/CUDA 真实训练/恢复不可在缺乏目标运行时或 GPU 的环境中推定完成。本源代码是待审的 G1-A draft，并未越过 Q0 阻断门。

## 3. DTO 与字段语义

- `MarketEvent`：`event_id`，`ts_event_ns`、`ts_init_ns`、`available_at_ns`（均 UTC `int64` 纳秒），`source_hash`（小写 SHA-256），`quality_grade`（DQ-A/B/C/D），`event_type` 与冻结的 `payload`。`require_available(decision_ts_ns)` 强制**可用时间不得晚于决策时刻**，并拒绝 DQ-D。
- `Observation`：固定有序的 `field_names/field_units/vector`；向量元素为**有限 float**；`account_state/risk_state/execution_state` 是冻结元数据；`prev_action` 为 Decimal；`available_through_ns <= decision_ts_ns`。具体 feature 顺序及单位由 L2 在消费方冻结，禁止临时重排。
- `PolicyAction`（`ActionIntent` 同一类别名）：`decision_id/policy_id/raw_action`，其中动作域为 `Decimal[-1,1]`；可选 `logprob_ref`。动作尚未经过风险与执行。别名不会生成第二套 wire schema。
- `TargetExposure`：`requested`、`soft_risk_adjusted`、`hard_risk_capped` **三个层次同时保留**；`unit` 强制显式。L1 不计算映射和上限。
- `ExecutionPlan`：`delta_qty` 及 `quantity_increment` 是 Decimal 且精度可整除；记录 `order_type/tif/cancel_policy/latency_model_id` 和标的/数量单位。执行策略逻辑由 L3 承担。
- `ExecutionSnapshot`：保留 orders/fills/positions、fees/funding/margin/equity/mark、currency 和 fact_source；`fees`/`funding` 与 `equity` **不能**默认为浮点。此 DTO 仅承载 L3 adapter 已证实的事实。
- `StepOutcome`：next Observation、Decimal reward、terminated/truncated、执行目标、barrier timestamp、evidence hash。结束与截断不能同时成立，next Observation 的时刻必须与 barrier 匹配。
- `ComputeRequest`：run/env/episode/step/model、observation schema hash、dtype、shape、payload hash；`correlation_key` 含全部逻辑关联字段；`ComputeResponse.require_match()` 严格检查请求一致。
- 其他 DTO：`EpisodeSpec`、`EngineFingerprint`、`EngineAdvanceResult`、`TerminalEvidence`、`InstrumentSpec`、`AccountView`、`RiskState`、`RiskDecision`、`ActorGenomeSpec`、`ModelRef`、`ESState`、`ComputeLease`、`RLConfig`、`ESConfig`。这些对象仅定义字段和基本不可变校验。

`FrozenFields` 仅承载 `(key, scalar)` 小型元数据的已排序唯一元组；不能包含 ndarray、Nautilus 私有对象或可变容器。对市场大数据应使用 L2 Arrow/Parquet 只读分区，而非进程间复制完整对象。

**参数单位责任边界**：观察 `field_units` 和敞口 `unit` 必须由提供方声明；MarketEvent 自定义 payload 的每字段单位必须由 L2 FeatureSpec/数据 schema 冻结，Snapshot 中订单/成交的详细单位由 L3 adapter 事件 schema 冻结。L1 并不推断交易规则或价格单位。

## 4. Schema、JSON 与 Arrow

- 当前编码协议 `schema_version = 0.4.0` / `protocol_version = 0.4.0`。
- 同一 `MAJOR.MINOR` 内的 patch 不能增删字段；新 minor **只能在末尾**追加提供 canonical JSON 默认值的可选字段。修改既有字段类型、顺序、单位、必填性必须申请 major/ICR。Major 升级未批准之前，不得擅自兼容。
- 解码始终严格拒绝：未知/缺失字段、保留标签、非有限数值、重复 JSON key、数字隐式 float/Decimal 转换、非 canonical 输入、不明 DTO 类型以及不匹配的当前 schema_version。**Schema 兼容性分析不代表可以在旧解码器中静默读取未来字段。**
- `canonical_bytes(obj)`：递归构造白名单 DTO，固定键序、无空格的 ASCII JSON；Decimal 使用精确字符串标签，float 使用 `hex()` 字符串标签，tuple 和枚举均带显式类型标签。`canonical_hash` 为 JSON bytes 的 SHA-256，独立于宿主平台文本编码。
- `from_canonical_bytes(blob)`：只按模块内已注册的 DTO 解码；不支持任意路径反射创建类、不使用 pickle。
- `to_arrow_ipc(tuple_of_DTO)`/`from_arrow_ipc(bytes)`：可选 pyarrow 依赖，将 canonical DTO bytes 及各行 SHA-256 放入 Arrow IPC record batch；跨进程**比较 canonical JSON hash，不依赖 Arrow 文件的内部物理字节完全相同**。仅用于小型元数据，不替代 L2 Arrow 数据契约。
- `dto_schema(name)` / `dto_schema_hash(name)`：公开字段顺序、类型描述符及当前 L1 声明的关键单位。必须用 ICR 维护跨开发线字段单位及特征命名。

## 5. Entry Points 与 Provider Registry

严格以四个 entry point group 注册，**由各实现包自行声明**其 entry point；L1 只发现，不写/复制任何实现包代码。

| Group | 类型 | 设计基线中的 Provider 名称 |
|---|---|---|
| `nautilus_rles.engine` | Engine | `nt_rc6` |
| `nautilus_rles.rl` | RL | `sb3` |
| `nautilus_rles.es` | ES | `evotorch` |
| `nautilus_rles.compute` | Compute | `local` |

`ProviderRegistry.discover(kind)`：返回唯一且稳定排序的 Entry Points；同一个 group 中重复 name **硬失败**。`load(kind,name)` 只在显式请求时加载已安装对象，并验证其 `kind`、`contract_version`（当前 major/minor）、`create(settings)` 和已安装 distribution 元数据。缺失、版本冲突、错误类型、依赖不存在或 provenance 缺失时，输出结构化异常，**不回退到硬编码 provider**。

消费方负责在调用 `create()` 后做完整静态 Protocol 和运行语义验证；L1 Registry **不会**自动安装第三方软件或证明训练 smoke PASS。

## 6. 配置契约

输入为由调用方使用可信解析器解析好的 YAML/JSON mapping（本包不强制引入 YAML 解析器）。`parse_config(mapping)` **恰好要求**以下根级段落：

| 分组 | 必填字段与允许值 |
|---|---|
| `runtime` | `python="3.14.7"`；`topology=audit/cpu/gpu/hybrid`；`research_sandbox=true` |
| `fold` | `scheme=N/N/N`；`step_days>=1`；`warmup/purge=auto` 或非负天数；`embargo="Nd"`；`terminal_policy=force_flatten_with_cost/mark_to_market` |
| `action` | `space=target_net_exposure`；`bounds=[-1,1]`；`deadband` 范围 `[0,1)` |
| `execution` | `policy=rebalance_market_like`；`pending_order_policy=cancel_replace/wait/fail`；`latency_model` 与 `fill_model` 为必填标识符 |
| `risk` | `hard_config`、`soft_params` 为**不同路径**；具体风控文件由 L3/Risk 包负责 |
| `compute` | `rl_lane=sync_vec`；`es_lane=async_candidates`；`max_cpu_workers>=1`；`gpu_owner>=0`；`fallback_policy=fail_fast`；`auto_select_by=end_to_end_wallclock` |
| `research` | baselines 从 `no_trade/always_long/simple_momentum/random_action` 选择，statistics 从 `block_bootstrap/deflated_sharpe/pbo` 选择；均不得为空或重复；`holdout_policy=one_shot` |

`resolve_config(mapping, auto_days={"fold.warmup": N, "fold.purge": M})` 对 `auto` 参数要求显式指定具体非负整数天数，未提供与多余覆盖均失败；生成**不修改原始输入**的冻结 `ResolvedConfig`、`source_hash` 和 `config_hash`。具体 warm-up 与 purge 长度计算属于 L2 / Research，不由 L1 猜测。

`HardRiskConfig` 和 `SoftRiskParams` 是不同类型与签名字段；`E2SearchSpace` 仅允许 `soft.exposure_multiplier`、`soft.drawdown_penalty`、`soft.turnover_penalty`。不支持通过 ES 搜索修改 Hard Risk，且不提供 fallback。

**安全基线**：Python 3.14.7 仅用于无真实 API key、无交易权限、隔离的研究运行面；连接 Paper/Live 需升级到已重新验证的安全版本并通过独立 Gate。配置结构校验不等于外部文件路径安全、具体 YAML 合法性或交易连接许可。

## 7. Run Identity、Manifest、SeedTree

`RunFingerprints` 必须填写 14 个 SHA-256：`dataset_hash`、`feature_hash`、`fold_hash`、`config_hash`、`code_hash`、`dependency_hash`、`seed_hash`、`adapter_hash`、`engine_hash`、`compute_hash`、`execution_hash`、`risk_hash`、`actor_hash`、`numeric_profile_hash`。加上 `protocol_version` 经 canonical hash 得到确定的 `run_id`；**任一指纹改变，新的 run_id 也随之改变**。

`ExperimentManifest` 保留 `run_id`、`attempt_id`（每次启动新的 UUID）、`protocol_version`、完整 `RunFingerprints`、`git_commit`、package versions、runtime、environment、algorithm、selection、artifact refs、`root_seed` 和 `seed_tree_hash`。Manifest 解析时校验运行指纹与 SeedTree 根种子的双向一致性；attempt retry 不允许暗改固定 run 的数据/算法或随机根种子。

`SeedTree(root_seed:uint64)` 与 `SeedPath((fold, stage, algo, env, worker, ...))` 通过域分离与长度前缀 HMAC-SHA256 派生 256-bit seed material / 64-bit child seed。相同根与路径可重现；不同路径采用密码学隔离；64-bit 投影**不能保证数学意义的绝对无碰撞**。重启相同逻辑 Worker 使用原 logical seed，新 attempt 使用新 `attempt_id`，二者不可混淆。

**不在 L1 承担的工作**：artifact staging→hash verify→atomic rename→COMPLETED marker（L6 Orchestrator/Compute）、模型 checkpoint 恢复、engine state 完整恢复、外部指纹的采集与真实性审计。

## 8. 结构化错误与 CLI 退出约定

`RLESError(category,code,message,run_id,cause_code)` 明确拒绝吞错或 silent fallback。`ErrorEnvelope` 固定 `schema_version/category/code/message/retryable/run_id/cause_code/exit_code`，由 `error_json(error)` 生成稳定 JSON。`cause_code` 仅包含脱敏错误代码，不序列化原始异常、访问密钥或堆栈。

| Category | Exit code | Retryable |
|---|---:|---|
| `config` | 2 | 否 |
| `contract` | 4 | 否 |
| `dependency` / `provider` | 3 | 否 |
| `data` | 4 | 否 |
| `runtime` | 70 | 否 |
| `transient` | 75 | **是** |
| `security` | 78 | 否 |

## 9. 构建、根级工程规范与交付边界

根 `pyproject.toml` 的 workspace wildcard 使各开发线交付后都能作为独立 packages 被发现；只在 `packages/contracts/` 创建了 L1 的真实 package。`packaging/workspace.py` 的静态 DAG 定义 11 个包且拒绝循环依赖；严格完整包检查只有所有外部工作线完成后才可能通过。

`requirements/cpu.in`、`requirements/cuda.in` **不是**可复现锁文件，更未验证 CUDA build/driver；最终锁必须由 CPython 3.14.7 目标运行环境解析所有 transitive wheel、SHA-256 及 license。具体 CUDA index/channel、runtime 和驱动必须以 NVIDIA GPU 实机训练/保存/恢复证据确定，不可“凭 wheel 存在判断 PASS”。`uv.lock` 和假冒的 hash 清单**不生成**。G0 阻断解除后，才可申领 Q0 正式验收并生成独立 wheel。

### 11.1 离线依赖与许可证审计流程

只有在 G0 环境实际解析出 **目标运行时 + 目标平台** 的完整 CPU 或 CUDA wheelhouse、精确版本/哈希锁和审查过的许可证清单后，`packaging/dependency_audit.py` 才有意义。输入是 `--wheelhouse`、`--lock`、`--licenses`、`--output`，所有输出都放在源码包之外的 G0 证据目录。

审查许可清单应采用 TOML 顶层 `[licenses]`，每个规范化 distribution 名字均填写 `{ spdx = "许可证单一 SPDX ID", reviewer = "签核人" }`；若未审批、来源不明、wheel SHA256 不匹配、存在同名多个构建或者许可证和 wheel 元数据冲突，则阻断。复合 SPDX 表达式当前不支持，需用户按许可流程单独审批后增强审计工具。该工具生成的 NOTICE 是包名、版本、SPDX 审批与 wheel SHA256 的**审查摘要**，不是替代第三方完整许可证/NOTICE 文本的法律交付件。

**注意：该工具验证 lock 内列出的 wheel，并不证明 lock 已包含全部传递依赖。** 完整传递闭包、CPU/CUDA 目标依赖解析、安装/训练、各许可证义务仍需外部 G0 Gate 验收。禁止将该工具的成功输出解释为 Q0 PASS。

### 11.2 标准 SeedPath.for_worker 参数

- `fold`：合法的非空逻辑 fold ID。
- `stage`：仅 `E1`、`R1`、`E2`。
- `algorithm`：`ppo`、`sac`、`td3`、`ddpg`、`pgpe`、`cma_es`。
- `env`、`worker`：`uint32` 非负编号；映射为固定 8 位十进制分段。
- `stream`：`python`、`numpy`、`torch`、`cuda`、`environment`、`es`。

生成路径的逻辑命名不会随 worker 物理进程 PID 或 retry attempt UUID 变化；同 run、同 fold、同分支重启维持同一个逻辑随机流。这里仅实现命名和 HMAC seed 派生，并不初始化或控制第三方框架 RNG。

## 12. 未决 ICR 与剩余阻断（R2 更新）

原 `ICR-L1-001`～`ICR-L1-004` 继续有效，以下是新增事项，不得由 L1 无审批改变其他工作线：

- **`ICR-L1-005`（Run Identity／算法身份绑定）**：当前 `RunFingerprints` 的 14 个字段均参与 `run_id`，但是 `ExperimentManifest.algorithm`、`selection`、`package_versions`、`runtime` 元数据本身不被强制校验为某个特定指纹的前像。如果消费者只改算法路线/选择规则而**没有同步修改 config/code/deps/actor 指纹**，有机会产生不同研究语义但相同 `run_id`。请 Chief Reviewer 决定是否在新 Minor/Major schema 中加入明确的 `algorithm_recipe_hash` 和 `selection_plan_hash`（或冻结 manifest→config 绑定规则）；在批准前消费者必须把所有算法、路线、超参、选择预算与运行配置写入 `config_hash` 所覆盖的冻结配置，不能仅修改独立 Manifest 文本字段。
- **`ICR-L1-006`（Hard/Soft Risk 签名语义）**：目前 `signature_hash` 具有严格的 SHA256 格式约束，但未定义签名计算前像或外部密钥认证机制；它**不能自动证明** HardRisk 配置文件不可篡改。请 L3 风控消费方与 Chief Reviewer 冻结签名前像、签发/认证主体、配置文件内容哈希与强制校验点。批准前不得把一个格式合格的 `signature_hash` 宣称为有效数字签名。
- **`ICR-L1-007`（Arrow / 子结构格式冻结）**：Arrow IPC 以每行 canonical JSON 与 SHA256 为轻量元数据传输格式；L2 大型 Arrow/Parquet 数据与 L3 orders/fills 子记录的单位和列级 schema 仍需跨线冻结。L1 不建立具体市场数据格式，也不将 Arrow 作为 PEP 508 核心强制依赖。
